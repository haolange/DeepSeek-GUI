## 1. 使用的系统/方法

仓库采用 **npm workspaces** 作为统一的包管理与依赖解析机制，根 `package.json` 通过 `workspaces: ["packages/*"]` 声明子包集合。所有第三方依赖（含 Electron、React、Tiptap、MCP SDK、better-sqlite3、node-pty 等）均通过 `dependencies` / `devDependencies` 在根 `package.json` 中集中声明，并由根级 `package-lock.json` 锁定版本。Kun 运行时核心位于独立目录 `kun/`，拥有自己的 `package.json` 和 `package-lock.json`，形成与 GUI 应用分离的依赖树；GUI 通过 `npm --prefix kun run build` 在其工作空间内安装并构建该运行时。

## 2. 关键文件与包

- `package.json`：根工作区入口，声明 Node 引擎要求 `>=22.19.0`、Electron 43.1.0、React 19、Vitest/Vite/Electron-vite 等开发依赖，以及运行期依赖如 `electron-store`、`electron-updater`、`@modelcontextprotocol/sdk`、`better-sqlite3`、`node-pty`、`openclaw`（指向本地 `vendor/openclaw-shim`）、`sharp`、`pdfjs-dist` 等。
- `package-lock.json`：锁定整个 workspace 的完整依赖图。
- `kun/package.json`：Kun 运行时私有包，通过 `file:` 引用同仓库内的 `@kun/extension-api`、`@kun/provider-catalog`、`create-kun-extension`，并在 `overrides` 中强制统一 `hono`、`undici`、`fast-uri` 等传递依赖版本。
- `packages/*/package.json`：扩展生态包（`@kun/extension-api`、`@kun/provider-catalog`、`@kun/extension-react`、`@kun/extension-test`、`create-kun-extension`），均为纯 TypeScript 库，仅声明自身构建/测试所需依赖。
- `scripts/postinstall.cjs`：安装后自动为 `better-sqlite3` 和 `node-pty` 执行 `prebuild-install --runtime=electron --target=<electron-version>`，确保 native 模块 ABI 匹配 Electron 二进制；同时修复 `node-pty` 预编译 `spawn-helper` 的可执行位。
- `scripts/check-packaged-runtime-dependencies.cjs`：构建后扫描 `out/main`、`out/preload` 中的 `import`/`require`/`import()`，提取外部包名并与 `package-lock.json` 比对，若发现打包产物引用了未列入生产依赖的包则报错，防止发布包缺失依赖。
- `resources/whisper/`、`resources/officecli/current/manifest.json`：以“资源包”形式随应用分发跨平台预编译二进制（whisper.cpp、OfficeCLI），不通过 npm 管理。

## 3. 架构与约定

- **单点声明 + lockfile 锁定**：除 `kun/` 子工程外，所有依赖集中在根 `package.json`，由 `package-lock.json` 固化版本，避免多工作区版本漂移。
- **workspace 内部包通过 `file:` 或 `npm workspaces` 解析**：GUI 对 `@kun/extension-api`、`@kun/provider-catalog` 使用 `^1.x` 语义范围，而 `kun/` 运行时使用 `file:../packages/...` 直接链接源码，保证开发时能即时修改。
- **依赖冲突通过 `overrides` 收敛**：根与 `kun/` 均在 `overrides` 中将 `hono`、`@hono/node-server`、`fast-uri`、`ip-address`、`undici` 等传递依赖固定到精确版本，避免不同子树引入不兼容版本。
- **原生模块 ABI 适配在 postinstall 阶段完成**：`postinstall.cjs` 在每次 `npm install` 后根据当前 `electron/package.json` 的版本重新下载/编译 `better-sqlite3` 和 `node-pty` 的 Electron prebuild，失败时降级为 JSONL 回退路径，保证离线/无编译器环境仍可运行。
- **发布前校验依赖完整性**：`check:packaged-runtime-deps` 脚本在 `build` 流程末尾执行，静态分析已编译 JS 中的动态 import，确保所有被引用的包都存在于生产依赖图中。
- **第三方二进制资源走专用目录而非 npm**：whisper.cpp 与 OfficeCLI 的二进制及其 manifest 放在 `resources/`，由 `scripts/prepare-whisper-runner.cjs`、`scripts/prepare-officecli.cjs` 在安装/打包阶段处理，不进入 `node_modules`。

## 4. 约定与约束

- **Node 版本约束**：根与 `kun/` 均声明 `engines.node >= 22.19.0`，要求开发者与 CI 使用满足该版本的 Node。
- **禁止遗漏生产依赖**：`scripts/check-packaged-runtime-dependencies.cjs` 会拒绝构建产物中引用但未列入 `package-lock.json` 生产依赖的包；该脚本被 `build` 脚本调用，构成硬性检查。
- **Electron 原生模块必须可加载**：`postinstall.cjs` 显式处理 `better-sqlite3`、`node-pty` 的 Electron prebuild 与权限问题，若失败仅警告但不中断安装，属于“尽力而为”的容错策略。
- **工作区内包版本同步**：根对 `@kun/extension-api`、`@kun/provider-catalog` 使用 `^1.x`/`^0.1.0` 语义范围，而 `kun/` 使用 `file:` 直连源码；发布时需将 `packages/*` 先构建并通过 `build:kun` 流程注入，避免发布旧版 API。
- **依赖升级需更新 overrides**：由于多处传递依赖（尤其是 hono/undici 生态）通过 `overrides` 强制对齐，升级任一上游包时需要同步调整两处 `overrides`，否则可能出现重复/冲突版本。
- **无私有 npm registry 配置**：仓库未发现 `.npmrc`/`.yarnrc` 等私有源配置，所有包从默认 npm registry 拉取；私有 shim `openclaw` 通过 `file:vendor/openclaw-shim` 本地引用。
- **无 vendoring 第三方 JS 源码**：`vendor/` 目录为空，JS 依赖全部经 npm 安装；仅二进制资源（whisper、officecli）以资源形式随应用分发。
